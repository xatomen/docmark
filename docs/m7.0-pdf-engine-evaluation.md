# M7.0 — Docmark Native PDF Engine evaluation

## Status

M7.0 is complete under the revised research and technology-selection scope. This report records confirmed repository facts and the initial dependency setup; it does not yet recommend a replacement engine.

The Markdown fixture is a reference and is not directly consumed by the current harness. The Chromium baseline is synthetic HTML and does not execute Docmark’s production print pipeline.

Reproduce with `pnpm pdf:poc:all`. Prerequisites: Python 3 with pypdf, Poppler (`pdfinfo`, `pdffonts`, `pdftotext`, `pdftoppm`), and Playwright Chromium (or `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`). Performance and bundle measurements are partial.

## Initial experiments and measured results

Run `pnpm pdf:poc`. The harness is isolated under `tests/pdf-poc/` and uses Playwright Chromium by default (override with `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`). It saves three PDFs to `artifacts/m7.0/`; the files are intentionally outside Git. The baseline is Chromium print-to-PDF of the equivalent local HTML fixture. The candidate PDFs are generated inside the browser by pdfmake 0.3.15 and PDFKit 0.21.0. The harness observed no non-local network requests during generation.

Observed artifacts (2026-11-27): baseline 61,417 bytes, pdfmake 22,411 bytes, PDFKit 3,440 bytes. All report two A4 pages. Chromium reports 595.92 × 842.88 pt, while the candidates report 595.28 × 841.89 pt. The harness measured approximately 231 ms from generation click through both downloads in this run; it is not a per-library isolated benchmark. Initialization and bundle measurements have not been isolated.

`pdffonts` reports Chromium subset embedded Liberation Sans/DejaVu and Noto Color Emoji fonts, all with Unicode mapping. pdfmake embeds subset Roboto Medium/Regular with Unicode mapping. PDFKit's default Helvetica/Courier Type 1 fonts are not embedded and have no Unicode mapping. `pdftotext` extracts Spanish and common punctuation from all three. PDFKit extraction visibly corrupts decomposed `café` (reported as `cafe0à`) and the technical arrows/inequality/other unsupported symbols; its built-in standard fonts are inadequate for this corpus. pdfmake preserves the decomposed accent as normalized `café`, but its candidate content currently omits some arrow symbols from the PDFMake document definition (fixture parity is not complete). Chromium retains decomposed text and symbol sequence. Emoji are visible/extracted in Chromium via Noto Color Emoji; candidate emoji behavior is not yet fully validated.

`pdftotext -layout`, multiple extraction engines, ToUnicode CMap inspection, visual raster comparison, link annotation inspection and exact order/spacing assertions remain to be run. The test harness's PDFKit table is plain text rather than a semantic table and does not establish table feature parity. Current candidate typography is not controlled: Chromium uses system fallback fonts, pdfmake uses bundled Roboto, and PDFKit uses standard Helvetica/Courier. Existing Docmark Montserrat is WOFF2 and has not yet been embedded. The extraction defects therefore mix font coverage/encoding and engine behavior; they do not isolate those causes.

Candidate sizes are compressed generated PDF sizes, not dependency or production bundle measurements. The candidates are devDependencies and have no imports from production code, but production bundle and Cloudflare Worker output sizes still need direct checks.

PDFKit with built-in fonts fails the current Unicode requirement. Keep the current print engine while performing a font-embedded PDFKit rerun or completing pdfmake fixture parity; select no replacement on current evidence.

## Final technology decision update (2026-11-27)

Following independent review, pdfmake is selected as the primary candidate for a future Docmark Native PDF Engine. This is a forward-looking M7.0 research decision; production export remains `window.print()`. The decision reflects successful browser generation, local execution, embedded subsets/Unicode mappings with registered Liberation Sans, useful composition/table/pagination features and lower expected integration complexity. PDFKit outputs remain retained as a technical comparator. The list extraction omission was corrected by representing all list entries as explicit top-level items. The browser print baseline now removes harness status and controls before capture. pdfmake external URI and internal `/GoTo` annotations are confirmed by annotation extraction. Code blocks still need an explicit monospace family; emoji are outside Liberation Sans coverage and fallback behavior is not yet standardized.

Advanced-document proof, embedded source attachments, interactive icon annotations/AcroForm fields, multipage repeating table headers, reliable headers/footers/page counters, TOC and Mermaid need implementation and structural verification before M7.0 acceptance. Manual validation in Adobe Acrobat Reader, Chrome, Edge and Firefox remains required; no cross-reader compatibility claim is made. M7.1 must not begin until M7.0 review and approval.

### Controlled typography rerun

The harness now registers the same four Liberation Sans TTF files (OFL 1.1, sourced from the system Liberation Fonts package) with browser CSS, pdfmake's VFS and PDFKit's browser font registration. Body size is 11 pt, line-height 1.4, A4 with 56 pt margins, and the same semantic corpus is represented in each engine. The Chromium print CSS and PDF candidates use Liberation Sans; code remains monospace in Chromium but is not yet consistently mapped in both candidate renderers. Browser emoji fallback is Noto Color Emoji; Liberation Sans itself does not cover emoji, so this is explicitly a fallback case.

Rerun outputs: 67,070-byte Chromium baseline, 31,280-byte pdfmake, 25,845-byte PDFKit (files under `artifacts/m7.0`). Each is two pages. Both candidate `pdffonts` reports now show embedded subset Liberation Sans with `uni=yes`; Chromium also uses embedded system fallback faces including Noto Color Emoji. `pdftotext` preserves Spanish, common punctuation and technical symbols in both candidates. It normalizes decomposed `café` to `café` in candidates while Chromium preserves the decomposed sequence. This points to extraction/text encoding normalization behavior; glyph coverage is confirmed by these test strings but does not establish all Unicode coverage. Emoji extraction appears absent/partial in the candidates despite a usable browser fallback. The two candidate definitions still differ in exact inline styling/table representation; content parity is improved but not exact.

Both candidates generate A4 two-page documents and embed external links; PDFKit creates an internal named destination. The current pdfmake internal destination does not yet have a separate verified target. `pdfinfo` validates dimensions/pages and `pdffonts` validates embedding/subsetting/ToUnicode flags. Link annotation destinations, second extractor (PDF.js), raster comparisons and multiple-run performance distributions are outstanding. Candidate PDF byte sizes are not library bundle sizes. No controlled library init-vs-repeat benchmark or production bundle delta has yet been obtained. The previous test's unknown external-request list was empty; the controlled rerun likewise has no non-local requests (local font assets are fetched from the harness server).

The prior weighted matrix is preliminary and should not be treated as a completed recommendation. On current evidence, both pdfmake and PDFKit meet a basic embedded-font/Unicode smoke test after registering identical TTFs; differences in line breaks and decomposed-accent extraction remain measurable, while emoji support and precise content parity are unresolved. Keep browser print as production export pending these checks.
