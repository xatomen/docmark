# M7.3 — Font & Unicode Engine

**Status: Phases A–E complete for the approved M7.3 scope and ready for independent code review.** Phase E compared generated artifacts in the available browser and extraction tools, audited fonts and PDF actions, and completed the requested regression sequence. This is not a claim of universal Unicode shaping or compatibility across every PDF reader; known gaps are listed below.

## Scope and boundary

The Phase A export path remains:

```text
Markdown → SemanticDocument → PDF adapter → font resolution plan → local TTF assets → pdfmake → PDF Blob
```

`DocumentSettings.typography.fontFamily` remains the single source of truth for the document family. The new registry consumes its existing IDs and does not alter settings, front matter, Markdown, the renderer-independent semantic model, or the HTML preview. Font bytes are not imported eagerly. The editor still exposes native PDF only in DEV; the existing preview, pagination, and `window.print()` export remain in use.

## Native registry and family resolution

`src/lib/pdf/fonts/types.ts`, `registry.ts`, `resolve-font.ts`, and `load-fonts.ts` are renderer-independent metadata/loading modules. They do not import React, the DOM, editor code, or font binaries. The registry records stable family IDs, display names/categories, four style faces, local paths, SHA-256, license, provenance, and document-family mappings. The default document family is Arial; the dedicated code family is Liberation Mono.

| Setting | Embedded regular/bold/italic/bold italic | Fidelity | User diagnostic |
|---|---|---|---|
| Arial | Liberation Sans | Approximate | Names the embedded Liberation Sans substitute |
| Helvetica | Liberation Sans | Approximate | Names the embedded Liberation Sans substitute |
| Georgia | Liberation Serif | Approximate | Names the embedded Liberation Serif substitute |
| Times New Roman | Liberation Serif | Approximate | Names the embedded Liberation Serif substitute |
| Courier New | Liberation Mono | Approximate | Names the embedded Liberation Mono substitute |
| Montserrat | Docmark Signature Sans | Exact outlines at static 400/700 faces | No family-substitution warning |

The pure resolver maps regular, bold, italic, and combined bold italic to a corresponding registered face. If a future family lacks a requested face, the deterministic order is: bold italic → bold → italic → regular; bold → regular; italic → regular. Such a fallback is reported. Unknown saved family values resolve through the default Arial mapping with a diagnostic. Phase A's current families all provide four faces, so that fallback path is unit-tested separately from production assets.

The adapter sets the resolved PDF family on default text, headings, inline runs, lists, and table cells. Inline code and fenced code use Liberation Mono; code tabs still expand to four spaces, and leading/trailing spaces, blank lines, and selectable text are retained. No syntax coloring or rasterization is used. Font-family, variant, Unicode, code-family, and unsupported-feature diagnostics are displayed after export. The native status/diagnostic element has a dedicated class hidden under `@media print`; document pages remain visible.

## Lazy loading, reuse, and privacy

The generator creates a font plan from the semantic document: selected family, used style variants, and a mono face only when code requires it. `load-fonts.ts` rejects paths outside `/fonts/` or the current origin, uses same-origin credentials and `redirect: "error"`, and caches the promise by local path. Concurrent/repeated calls share the request; failed promises are removed so the same asset can be retried. Font metadata remains separate from loaded byte arrays. The generator registers only the selected native family/families in pdfmake's browser VFS and never preloads all registry assets.

Playwright verified no native TTF or pdfmake request during ordinary DEV editor startup, only the selected family's used faces and required mono face on export, error recovery, and zero repeated font requests on a second export in the same page. The Phase A Montserrat-plus-code observation (37 startup resources, 684 ms cold/358 ms repeat export, five font faces) remains historical; see `resource-measurements.json`. In the Phase B primary-only/fallback DEV scenario, startup had 34 resource entries and no PDFMake/font resource. Primary-only export took 536 ms and requested the Liberation Sans regular face; fallback export took 242 ms and fetched Docmark Signature Sans regular; repeated fallback export took 288 ms and fetched no additional font. The observed resource bodies totaled 4,333,702 bytes across the pdfmake chunks and both font files; the primary-only path totaled 3,958,810 bytes. This is one local DEV measurement, not a budget or production benchmark. Requests remained same-origin, and the generated-PDF acceptance harness blocked external HTTP(S) requests and observed none.

Measured resource/timing results are in `artifacts/m7.3/resource-measurements.json` and the font/pdfmake transfer records are in `validation-report.json`. These values are observations, not performance thresholds. Browser Resource Timing's `transferSize` is the compressed transfer measurement; response-body sizes are also recorded separately. The editor cold export measurement uses Next's DEV runtime, and the PDFMake module is requested only when the user activates native export. This is not a Worker bundle-size benchmark.

## Phase B — Coverage, graphemes, and fallback

### Coverage generation and metadata

`scripts/generate-pdf-font-coverage.py` reads the exact registered TTF assets with development-only `fontTools==4.61.1`. It reads Unicode cmap subtables, keeps valid Unicode scalar values mapped to nonzero glyph IDs other than `.notdef`, merges adjacent code points into inclusive ranges, and records per-file SHA-256, byte size, glyph count, and range count. Each variant has its own record. The generated minified metadata is `src/lib/pdf/fonts/coverage.generated.json` (34,104 bytes for 18 native faces in this tree); it is imported from the lazy native-PDF path, not editor startup. Phase C added 5,089 bytes of cmap metadata for DejaVu Math TeX Gyre (2,112 code points/188 ranges) and Noto Sans Symbols2 (2,655/166).

Reproduce and detect stale metadata with:

```sh
python3 -m pip install fonttools==4.61.1
python3 scripts/generate-pdf-font-coverage.py
python3 scripts/generate-pdf-font-coverage.py --check
```

Generation checks that the file set and hashes match `registry.ts`; acceptance also runs `--check`. At runtime, a path/hash mismatch is treated as unavailable coverage and reported, never trusted as a successful cmap match. Lookup uses binary search over compact ranges; no font binary is parsed in the browser. Current per-face counts are Sans 2,327 code points/125 ranges; Serif 2,321–2,329/127–129; Mono 2,305/129; Docmark Signature Sans 1,312/165. The different values confirm that variants are not assumed identical. The generated ranges are evidence of cmap mappings, not a promise that the glyph shapes or shaping are correct.

### Segmentation, normalization, and source preservation

`fonts/unicode.ts` uses `Intl.Segmenter` with grapheme granularity. If unavailable, native generation reports a visible export error instead of splitting UTF-16 or combining sequences. Tests cover precomposed/decomposed Spanish, multiple marks, supplementary scalars, variation selectors, a skin-tone/ZWJ sequence, regional indicators, spaces, CRLF, and empty text. Runs retain original code points until they reach pdfmake. Clusters containing variation selectors, ZWJ, emoji modifiers, regional-indicator pairs, keycap marks, or tag characters are reported unresolved unless a future implementation explicitly qualifies that full sequence. This prevents a false claim based on per-code-point cmap matches. The semantic model, Markdown, links, filenames, and editor code do not normalize text.

The Phase C investigation locates the composition in fontkit 3.0.0, before PDFKit builds ToUnicode: `DefaultShaper.assignFeatures` calls `composeGlyphs`, which decomposes a cluster and recomposes a cmap-supported NFC scalar. PDFKit then stores each shaped glyph's `codePoints` in its Unicode map. The generated CMap for the comparison fixture maps U+00E9 and has no U+0301 mapping. Markdown parsing, Docmark segmentation, resolver output, and the semantic document retain source code points. pdfmake's public `fontFeatures` option reaches PDFKit, but a real PDF probe with `{ccmp:false, liga:false}` still extracts NFC.

Exact extraction therefore fails for NFD in plain prose, inline code, and fenced code: for example, source `cafe + U+0301` emits U+00E9 in both PDF.js 6.5.438 and Poppler 25.03.0. All tested outputs remain canonically equivalent; they are not exact code-point or source-byte matches. Stacked `a + U+0308 + U+0304` similarly emits U+01DF. Docmark never normalizes source and never applies NFKC.

PDFKit 0.21.0 does expose `markContent("Span", { actual })`. A direct PDFKit probe shows it writes `/ActualText` and Poppler honors the decomposed string, but this PDF.js version ignores the non-structural ActualText span and extracts the visible NFC glyph. pdfmake does not expose a supported per-inline ActualText option or render hook. Phase C therefore does not patch or monkey-patch renderer internals. The direct API experiment is preserved separately as `pdfkit-actualtext-nfd-probe.pdf` and is not a production export result.

### Deterministic fallback policy

`fonts/coverage.ts` validates metadata hashes and does range membership. `fonts/resolve-text-runs.ts` resolves each grapheme cluster as a unit. It tries the requested embedded face first, then the requested style in this stable family order:

| Requested category | Fallback order after selected primary |
|---|---|
| Sans serif | Liberation Sans → Docmark Signature Sans → Liberation Serif → Liberation Mono → DejaVu Math TeX Gyre → Noto Sans Symbols2 |
| Serif | Liberation Serif → Liberation Sans → Docmark Signature Sans → Liberation Mono → DejaVu Math TeX Gyre → Noto Sans Symbols2 |
| Monospace | Liberation Mono → Liberation Sans → Docmark Signature Sans → Liberation Serif → DejaVu Math TeX Gyre → Noto Sans Symbols2 |

After all families have been tried at the requested variant, it tries that variant's fixed approximate-style order. A matched non-primary family or a non-requested variant is marked as approximate. Adjacent runs merge only when family, variant, and resolution state match. Bold, italic, bold italic, strikethrough, links, line breaks, table alignment, and existing list/code structures remain on the same renderer-local runs. The semantic model is unchanged.

Measured real gaps and fallbacks: U+20BD RUB sign uses Docmark Signature Sans; U+2208 ELEMENT OF and U+21D2 RIGHTWARDS DOUBLE ARROW use DejaVu Math TeX Gyre; U+27E8/U+27E9 mathematical angle brackets are also covered by it. The single-face Noto Sans Symbols2 fallback covers standalone U+1F512 LOCK and U+26A0 WARNING SIGN. Each was generated through the production browser/pdfmake pipeline, embedded as a subset with a Unicode map, extracted by PDF.js and Poppler, and visually inspected in the saved raster previews. Math and pictograph faces load only when their mapped glyphs are in the document.

### Unresolved glyph policy and qualified coverage

If no registered face covers every scalar in a grapheme, the PDF text uses an explicit ASCII marker such as `[U+1F600]` in place of that cluster. Diagnostics name the original cluster/code points, say that the PDF uses a marker, and confirm that Markdown/semantic text is unchanged. Warnings are grouped by issue/family/variant and capped at 20 user-facing diagnostics plus category summaries. Unsupported glyph, unsafe-link, and fidelity warnings are prioritized above successful fallback notices. Private-use-area characters are resolved only in the requested primary family; no unrelated fallback family may supply them. The marker makes loss visible and keeps unsupported code points searchable by their code-point label; it is not a rendering of the original glyph.

Acceptance verified samples of Basic/extended Latin, Spanish, Greek, Cyrillic, technical punctuation, currencies, selected math operators and arrows, ligature-sensitive words, and combining marks. Actual fallback is verified for RUB, ELEMENT OF, RIGHTWARDS DOUBLE ARROW, mathematical brackets, lock, and the plain warning sign. Complete Unicode blocks are not qualified. U+2208/U+21D2 were upgraded from marker to DejaVu glyphs in Phase C; U+1F600, U+1F680, U+2705, U+274C, and U+1F4C4 remain explicit markers. cmap data alone does not prove mark positioning, ligatures, bidi order, or complex shaping.

Phase C adds only two open static font files (1,234,044 bytes total) after their measured gaps and PDF compatibility were demonstrated; no runtime dependency was added and there are no external font requests. Coverage metadata increased from 29,015 to 34,104 bytes, a 5,089-byte increase for the two per-variant cmap records. Noto Color Emoji is not bundled. Standalone lock and warning glyphs are monochrome; ⚠️ with VS16 is deliberately rejected as a sequence. The loader remains lazy and repeats reuse loaded fonts. The final editor E2E measured 34 startup resources and no PDF/PDF-font load; exporting basic Latin requested only 410,820 bytes of Liberation Sans. Later exports separately requested 577,192 bytes for math and 656,852 bytes for Noto Symbols2. Repeat math and symbol exports each made zero new font requests. Times and transfer values are one local DEV run, not thresholds.

## Phase D — Integration, reliability, and font-loading performance

Phase D consolidated font selection around the actual `ResolvedTextRun[]` produced by the adapter. The unused document-wide pre-scan was removed so only font faces used in final runs are planned and loaded. The editor still lazy-loads pdfmake and fonts only after the user starts export. A browser-session test exports Arial, Georgia, Courier New, Montserrat, math/pictograph fallbacks, mixed styles and repeated documents, checks actual embedded faces, and verifies that switching back to Georgia does not reuse incompatible family descriptors. Cache unit tests cover concurrent request deduplication, successful reuse and retry after failed loads.

The latest actual DEV editor measurement (`font-loading-benchmark.json`) observed 33 startup resources and zero pdf/PDF-font requests. Cold primary export requested 410,820 font bytes and generated a 7,006-byte PDF in 480 ms. Initial Montserrat export requested two faces (749,880 bytes); math and pictograph cases requested 577,192 and 656,852 bytes respectively. Three additional style faces for a mixed document requested 1,239,596 bytes. Two repeated mixed exports requested zero new font bytes (403 and 423 ms; median 413 ms). The first export also downloaded pdfmake chunks totaling 3,547,990 response-body bytes. All measured requests came from the local editor origin. These are single-run environment observations, not performance budgets.

pdfmake 0.3.15 retains decoded VFS buffers for every previously used face for the browser session and provides no supported eviction API. Docmark caches raw font `Uint8Array`s and deduplicates loads. We do not mutate pdfmake internals to evict fonts. The artifact records these retention semantics and verifies family switching remains correct.

Phase D also bounds export diagnostics (20 distinct messages, 240 characters each), reports decomposed Unicode fidelity concerns without changing source, and replaces Hebrew/Arabic/bidi-controlled graphemes with explicit code-point markers because correct bidi ordering is unavailable. The source Markdown and semantic document remain unchanged. Font inventory acceptance checks the registered asset set, hashes, TrueType headers, internal names and retained license notices.

An optional static subsetting experiment preserved the full tested Unicode cmap and shaping tables in temporary candidates and passed PDF.js/Poppler extraction checks. It reduced the two candidate files from 1,234,044 to 1,138,496 bytes (95,548 bytes, 7.74%); DejaVu lost only FFTM and Noto lost DSIG. Production font assets were left unchanged because this modest saving did not justify modified-font provenance and maintenance in this phase. Candidates and previews are retained under `artifacts/m7.3/font-subset-candidates/`.

## Validation and artifacts

### Review corrections: integrity, diagnostics, and private-use characters

The browser font loader rejects empty or malformed TrueType responses and validates every downloaded face against its registry SHA-256 with Web Crypto before caching it. Font requests use `cache: "no-store"`; only a verified response is retained under a path-and-hash cache key, while a failed request clears its pending entry so the next export can retry. Same-origin path checks, redirect rejection, lazy loading, and concurrent request deduplication remain in place. Unit tests cover corrupt HTTP 200 bodies and recovery, and the DEV Playwright case verifies failure, retry without reload, and reuse of validated bytes.

Diagnostics are grouped and bounded. Unsupported glyphs, unsafe links, and fidelity warnings take priority over successful fallback notices; the PDF adapter emits at most 20 user-facing warnings plus category summaries. A regression case confirms that more than 20 supported fallback characters do not hide a later unsupported emoji marker. Messages identify requested and resolved family/variant. Private-use-area characters are never borrowed from unrelated fonts: they resolve only in the selected primary family or produce an explicit code-point marker.

The final diagnostic consistency correction explicitly classifies `Qualified shaping is unsupported` and `Private-use fallback from unrelated font families is disabled` as unsupported content. Tests confirm both precede successful fallback messages. The maximum includes the omission summary: 19 candidates remain 19 warnings, 20 remain 20, and 21 or more produce no more than 19 entries plus one summary. A 70-candidate test confirms that omissions from the internal 64-candidate bound and the visible warning limit are both counted.

For this final correction, `pnpm lint`, `pnpm exec next typegen`, `pnpm exec tsc --noEmit`, `pnpm test:unit` (**333/333**, 22 files), `pnpm build`, and `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH="$CHROMIUM_BIN" pnpm pdf:native:acceptance` (**45 documents**) passed. The focused DEV Playwright diagnostic test passed **1/1** with unsupported shaping and PUA markers ranked ahead of successful fallbacks. The full regression results recorded above were not rerun as part of this correction.

The reproducible browser acceptance command uses Docmark’s semantic model, PDF adapter, coverage resolver, local font loader, and pdfmake. The final run generated and checked **45 production-pipeline documents**, including NFC/NFD, inline and fenced code, symbols, pictographs, script-boundary markers, and integrated technical/fallback documents. These are local DEV observations, not production performance budgets. Export generation includes browser-side work; timings vary by environment.

The optional static subsetting probe saved 95,548 bytes (7.74%) across two temporary candidates. Distributed production fonts were not changed by that experiment. The regenerated ZIP contains the PDF set, validation JSON, screenshots and reports; see [`artifacts/m7.3/README.md`](../artifacts/m7.3/README.md) and [`docs/m7.3-phase-e-review.md`](m7.3-phase-e-review.md).

## Known limitations

- System font settings map to disclosed open alternatives; proprietary system fonts are not embedded.
- Docmark Signature Sans uses OFL-compliant renamed static Montserrat instances, so its PDF internal family name differs from HTML’s Montserrat name. The build reproducibility check freezes the source timestamp.
- Coverage is limited to registered faces and cmap mappings; cmap presence does not guarantee shaping or correct glyph appearance. Only two isolated monochrome pictographs are qualified, not general emoji support.
- Unsupported clusters become `[U+…]` markers with export diagnostics. Japanese, Chinese, Korean, Arabic, Hebrew, and Devanagari samples remain unsupported or marked. RTL reading order and complex shaping are not implemented.
- Variation selectors, ZWJ, modifiers, regional indicators, keycap, and tag sequences remain unqualified and use a whole-cluster marker.
- pdfmake/fontkit canonical-composes NFD text before ToUnicode extraction, including in code, despite preserving original Markdown and semantic text. Exact NFD extraction is unresolved.
- pdfmake retains decoded VFS font buffers for the browser session and has no supported eviction API. Docmark caches and reuses downloaded bytes; it does not mutate pdfmake internals.
- Browser reader inspection covered Chromium only. PDF.js was used as a text extractor, not its GUI viewer. Adobe, Firefox, Edge and search behavior still require manual checks in those readers.
- Resource size and timing observations are local DEV measurements, not production budgets. The Worker bundle was not benchmarked here.
- PDFKit ActualText and candidate color-font probes are isolated research artifacts, not production output.

Phase E is complete for M7.3’s font/Unicode implementation and evidence scope. The documented Unicode and reader limitations remain explicit follow-up decisions; no critical or high-severity blocker was found in the review. M7.3 is ready for independent code review. M7.4 has not started.
